## 二、架构概览（四大核心要素 / 执行本质）

LangGraph 将 AI 工作流抽象为一张 **有向图（Directed Graph）**：

```
用户调用 graph.invoke(initial_state)
   ↓ ① START                      图的虚拟起始节点（触发第一条边）
   ↓ ② Node（节点）                执行业务逻辑，读取 State，返回增量字典
   ↓   ↕ State（状态）             节点间流转的共享数据容器
   ↓ ③ Edge（边）                  控制执行顺序（普通边 / 条件边）
   ↓ ④ END                        图的虚拟终止节点（执行结束）
返回最终 State 给调用方
```

| 要素    | 作用          | 类比         | 关键 API                                   |
| ----- | ----------- | ---------- | ---------------------------------------- |
| State | 节点间流转的共享数据  | 流水线上的"托盘"  | `TypedDict` / `Pydantic`                 |
| Node  | 执行具体逻辑的函数   | 流水线上的"工站"  | `add_node(name, fn)`                     |
| Edge  | 控制执行顺序和路由   | 流水线上的"传送带" | `add_edge()` / `add_conditional_edges()` |
| Graph | 将三者组装成完整工作流 | 整条"流水线"    | `StateGraph` → `compile()`               |

```
LangChain ──→ 擅长"链"：A → B → C（线性，适合简单管道）
LangGraph ──→ 擅长"图"：任意有向图，支持循环、分支、并行（适合复杂 Agent）
```

```
invoke(initial_state) 的执行过程：
  1. 将 initial_state 写入全局 State
  2. 从 START 触发，找到第一条边（add_edge(START, "first_node")）
  3. 执行对应节点函数 node(state) → delta_dict（增量字典）
  4. 用 Reducer 将 delta_dict 合并到全局 State
  5. 根据出边（普通边 or 条件边）找下一个节点
  6. 重复 3-5，直到到达 END
  7. 返回最终 State
```

### 2.1 最小完整示例（Hello LangGraph）

```python
# ============================================================
# 最简单的 LangGraph 图：展示四大要素的完整组合
# ============================================================
from typing import TypedDict                         # 导入类型字典，用于定义 State 结构
from langgraph.graph import StateGraph, START, END   # 导入图构建核心类和特殊节点标记


# ── 第一步：定义 State（节点间流转的共享数据）──────────────────────────────
class HelloState(TypedDict):
    """State 类：定义图中各节点共享的数据结构（TypedDict 方式）"""
    message: str   # str: 在节点间传递的消息字符串


# ── 第二步：定义 Node 函数（执行具体业务逻辑）──────────────────────────────
def say_hello(state: HelloState) -> dict:
    """节点函数：读取 state 中的 message，添加问候语后返回增量字典"""
    # state["message"] -> str: 读取当前 State 中 message 字段的值
    return {"message": f"Hello, {state['message']}!"}  # dict: 只包含本次修改的字段


# ── 第三步到第六步：创建图 → 添加节点 → 添加边 → 编译 ──────────────────────
graph = StateGraph(HelloState)           # StateGraph(schema) -> StateGraph: 创建以 HelloState 为状态模式的图
graph.add_node("hello", say_hello)       # add_node(name, fn): 注册节点，name 为字符串标识符
graph.add_edge(START, "hello")           # add_edge(src, dst): 添加普通边，START → hello
graph.add_edge("hello", END)             # add_edge(src, dst): 添加普通边，hello → END

app = graph.compile()                    # compile() -> CompiledGraph(Runnable): 编译图，生成可执行对象；实现 Runnable 接口，支持 invoke / stream / batch 等方法

# ── 执行图 ─────────────────────────────────────────────────────────────────
# invoke(input_dict) -> dict: 同步执行图，返回最终 State 字典
result = app.invoke({"message": "LangGraph"})   # dict: 传入初始 State
print(result)   # dict: 输出 {'message': 'Hello, LangGraph!'}
```

## 三、State（状态）

State 是在整个图执行过程中，在节点之间传递和共享的 **数据容器**。

- 每个节点接收 **完整的当前 State** 作为输入
- 节点执行后返回一个 **增量更新字典**（只包含本次修改的字段）
- LangGraph 负责将增量字典 **合并（Reduce）** 到全局 State 中

### 3.1 State 的三种定义方式

#### 3.1.1 TypedDict（最常用）

```python
# ============================================================
# 方式一：使用 TypedDict 定义 State（推荐方式）
# 优点：有类型提示，IDE 自动补全，零运行时开销
# ============================================================
from typing import TypedDict   # 导入 TypedDict，用于定义带类型标注的字典类

class BasicState(TypedDict):
    """基础 State 类：定义图中各节点共享的数据字段"""
    user_input:   str    # str: 用户输入的原始文本
    response:     str    # str: 模型返回的响应文本
    count:        int    # int: 计数器，记录执行次数
    process_data: dict   # dict: 中间处理结果，存储任意键值对
```

> **增量更新的三种情况**
>
>
> | 情况                      | 说明                           |
> | ----------------------- | ---------------------------- |
> | 节点返回了某字段                | 该字段按 Reducer 规则更新（默认覆盖）      |
> | 节点未返回某字段                | 该字段保持当前值不变                   |
> | 字段在 TypedDict 中定义但初始未传入 | 节点首次返回该字段时相当于"新增写入"，之后正常参与更新 |
>
>
> **注意**：节点**不能**返回 TypedDict 中未声明的字段，LangGraph 的类型校验会拒绝未知字段。若需要所有字段均为可选（初始化时可不传），可在 TypedDict 中加 `total=False`：
>
> ```python
> class MyState(TypedDict, total=False):
>     counter: int   # 可选字段，初始化时可不传，节点首次返回时写入
>     name: str      # 可选字段
> ```
>
> **State 的结构必须提前声明（"写死"）**：与普通 `dict` 不同，LangGraph 的 State 不允许在运行时动态添加字段。所有可能用到的字段都必须在 TypedDict 中事先定义好。这样设计的原因：
>
> - 多节点共享 State 时，每个节点都能明确知道有哪些字段
> - Reducer 需要提前知道每个字段的合并策略
> - 防止节点意外写入未知字段污染全局 State
>
> 若确实需要承载动态内容，可在 State 中声明一个 `dict` 类型字段作为"容器"：
>
> ```python
> class MyState(TypedDict):
>     counter: int
>     extra: dict   # 用该字段承载运行时动态产生的任意键值对
> ```
>
> **读（访问）和写（返回）是两件事**：字段"首次出现在 State 里"靠的是某个节点**返回**它，而不是**读取**它。节点可以直接 `return {"name": "Alice"}` 而无需先读 `state["name"]`。只有**读取**一个尚未写入的字段才会抛 `KeyError`：
>
> ```python
> # ✅ 安全：node_a 直接返回 name，不需要先读
> def node_a(state): return {"name": "Alice"}   # 写入，name 此后存在于 State
>
> # ✅ 安全：node_b 在 node_a 之后执行，name 已存在
> def node_b(state): return {"greeting": f"你好，{state['name']}"}
>
> # ❌ 危险：node_c 在任何节点写入 name 之前就读取它
> def node_c(state): return {"result": state["name"]}  # KeyError！name 还不存在
> ```
>
> 若节点需要安全读取可能尚未写入的字段，应使用 `state.get("name", 默认值)` 兜底。

#### 3.1.2 dict（快速原型）

```python
# ============================================================
# 方式二：直接使用 dict（不做类型校验，适合快速原型验证）
# 优点：零配置；缺点：没有类型提示，字段错误不会在编写时报错
# ============================================================
from langgraph.graph import StateGraph  # 导入 StateGraph

# StateGraph(dict): 以 dict 作为状态模式，不做任何类型验证
graph = StateGraph(dict)  # StateGraph: 最简单的无类型约束图
```

#### 3.1.3 Pydantic BaseModel（需要数据校验）

```python
# ============================================================
# 方式三：使用 Pydantic BaseModel（需要严格数据校验的场景）
# 优点：自动类型校验、字段验证；缺点：有运行时开销
# ============================================================
from pydantic import BaseModel   # 导入 Pydantic 基础模型类
from typing import Optional      # 导入 Optional，表示字段可以为 None


class MyState(BaseModel):
    """Pydantic State 类：字段赋值时会自动校验类型"""
    x:      int            # int: 整数字段（必填），赋值时自动校验类型
    result: Optional[str] = None   # Optional[str]: 可选字符串，默认为 None
```

### 3.2 Reducer（规约器）—— State 更新的核心机制

**核心问题**：当节点返回 `{"bar": ["bye"]}` 时，LangGraph 如何将其合并到当前 State？

**答案**：由 **Reducer 函数** 决定。

#### 3.2.1 默认 Reducer：直接覆盖

```python
# ============================================================
# 默认 Reducer：不指定任何 Reducer，新值直接覆盖旧值
# 适用场景：单值字段，如 step/flag/response
# ============================================================
from typing import TypedDict, List   # 导入类型标注工具

class DefaultReducerState(TypedDict):
    """默认 Reducer 示例：字段未指定 Reducer，新值覆盖旧值"""
    foo: int          # int: 整数字段，节点返回新 foo 值时直接覆盖
    bar: List[str]    # List[str]: 列表字段，节点返回新列表时直接覆盖（非追加！）

# ── 执行流程 ──────────────────────────────────────────────────
# 初始状态: {"foo": 1, "bar": ["hi"]}
# node1 返回: {"foo": 22}              → 覆盖 foo，bar 不变
# node2 返回: {"bar": ["bye1","bye2"]} → 覆盖 bar，foo 不变
# 最终结果: {"foo": 22, "bar": ["bye1", "bye2"]}
```

#### 3.2.2 operator.add Reducer：加法/拼接归约

```python
# ============================================================
# operator.add Reducer：等价于 Python 的 + 运算符，对旧值与新值执行加法/拼接
# 适用类型：
#   - List  → 列表拼接（最常见，适合 Map-Reduce 收集结果）
#   - str   → 字符串拼接
#   - int/float → 数值累加
#   - tuple → 元组拼接
# 注意：类型必须支持 + 运算符，否则运行时报 TypeError
# ============================================================
import operator                                   # 导入 operator 模块，提供 add 函数
from typing import Annotated, List, TypedDict    # Annotated 用于携带元数据（Reducer 函数）

class ListAddState(TypedDict):
    # Annotated[类型, Reducer函数]
    # LangGraph 读取第二个参数作为合并函数
    data: Annotated[List[int], operator.add]  # List[int]: 每次更新追加，不覆盖

# ── 执行流程 ──────────────────────────────────────────────────
# 初始状态:   {"data": [0]}
# node1 返回: {"data": [1, 2]}  → 追加 → [0, 1, 2]
# node2 返回: {"data": [3, 4]}  → 追加 → [0, 1, 2, 3, 4]
# 最终结果: {"data": [0, 1, 2, 3, 4]}
```

#### 3.2.3 add_messages Reducer：对话消息专用

```python
# ============================================================
# add_messages Reducer：LangGraph 对话图的标准写法
# 三种操作语义：
#   1. 追加（Append）：新消息 id 不在历史中 → 追加到列表末尾
#   2. 替换（Update）：新消息 id 与历史中某条相同 → 原地替换，列表长度不变
#      - 消息 ID：LangChain 消息对象（HumanMessage / AIMessage 等）自带的 id 字段
#      - 不手动指定时由 LangChain 自动生成 UUID；手动指定相同 id 可触发替换
#      - 用途：流式输出修正、工具调用结果更新等需要原地更新消息的场景
#      - 例：AIMessage(id="msg-001", content="旧内容") 被
#           AIMessage(id="msg-001", content="新内容") 替换，列表长度不变
#   3. 删除（Delete）：返回 RemoveMessage(id=...) → 将对应 id 的消息从列表移除
#      - 用途：裁剪上下文长度（Token 限制）、清除中间过程消息等
#      - 例：RemoveMessage(id="msg-001") → 列表中 id="msg-001" 的消息被移除
# 适用场景：任何需要维护对话历史的多轮 Chat Agent
# ============================================================
from langgraph.graph.message import add_messages         # 导入 LangGraph 内置的消息专用 Reducer
from langchain_core.messages import (
    HumanMessage,    # 用户发送的消息类型
    AIMessage,       # AI 回复的消息类型
    RemoveMessage,   # 删除信号：携带 id，告知 add_messages 移除对应消息；自身不保留在列表中
)
from typing import Annotated, List, TypedDict            # 导入类型标注工具

class AddMessagesState(TypedDict):
    # Annotated[类型, Reducer 函数]
    messages: Annotated[List, add_messages]   # List: 对话消息列表，由 add_messages 管理

# ── 操作一：追加 ───────────────────────────────────────────────
# 初始状态: {"messages": [HumanMessage(id="m1", content="你好")]}
# node1 返回: {"messages": [AIMessage(id="m2", content="你好！")]}
#   → id="m2" 不在历史中 → 追加
#   → [HumanMessage(id="m1"), AIMessage(id="m2")]

# ── 操作二：替换（按 id 去重）──────────────────────────────────
# node2 返回: {"messages": [AIMessage(id="m2", content="你好，有什么可以帮你？")]}
#   → id="m2" 已存在 → 原地替换，列表长度不变
#   → [HumanMessage(id="m1"), AIMessage(id="m2", content="你好，有什么可以帮你？")]

# ── 操作三：删除（RemoveMessage）──────────────────────────────
# RemoveMessage 是一个只携带 id 的"删除信号"，自身不会留在列表中
# node3 返回: {"messages": [RemoveMessage(id="m1")]}
#   → add_messages 识别到 RemoveMessage → 将 id="m1" 的消息从列表移除
#   → [AIMessage(id="m2", content="你好，有什么可以帮你？")]
#
# 典型用途：
#   - 裁剪历史（Token 超限时删除最早的消息）
#     to_delete = [RemoveMessage(id=m.id) for m in state["messages"][:-10]]
#   - 清除工具调用中间消息，仅保留最终对话轮次
```

| Reducer        | 行为        | 适用场景               |
| -------------- | --------- | ------------------ |
| 默认（无标注）        | 新值覆盖旧值    | 单值字段，如 step / flag |
| `operator.add` | 加法/拼接归约（`+` 运算符） | 列表收集、字符串拼接、数值累加 |
| `add_messages` | 消息追加 / 替换 / 删除 | 对话历史消息             |
| 自定义函数          | 任意合并逻辑    | 复杂业务规则             |

## 四、Node（节点）

Node 是图中 **执行具体业务逻辑的函数**。

- **输入**：完整的当前 State（`dict` 或 `TypedDict` 对象）
- **输出**：增量字典，只包含本次修改的字段
- LangGraph 自动将返回值通过 Reducer 合并到全局 State

### 4.1 节点函数签名

```python
# ============================================================
# 标准节点函数签名：接收 state，返回增量字典
# ============================================================
from typing import TypedDict   # 导入 TypedDict

class MyState(TypedDict):
    """示例 State：用于演示节点函数的增量更新行为"""
    counter: int    # int: 计数字段，由节点每次递增
    name: str       # str: 名称字段，本节点不修改它，演示"未返回字段保持原值"


def my_node(state: MyState) -> dict:
    """
    标准节点函数
    Args:
        state (MyState): 完整的当前 State，包含图中所有字段的最新值
    Returns:
        dict: 增量字典，只包含本次修改的字段；LangGraph 将其合并到全局 State
    """
    value = state["counter"]    # int: 读取 counter 字段的当前值
    result = value + 1          # int: 执行业务逻辑（此处为简单递增）
    # 只返回需要更新的字段：counter 被更新，name 未包含 → name 保持原值不变
    return {"counter": result}  # dict: 增量字典，LangGraph 负责合并
```

### 4.2 带额外参数的节点（functools.partial）

```python
# ============================================================
# 带额外参数的节点：使用 functools.partial 绑定非 State 参数
# 场景：节点函数需要超参数（如阈值、配置项），但不适合放在 State 中
# ============================================================
from functools import partial                            # 导入 partial，用于固定函数部分参数
from langgraph.graph import StateGraph, START, END       # 导入图构建组件

def process_node(state: dict, param1: int, param2: str) -> dict:
    """
    带额外参数的节点函数
    Args:
        state  (dict): 完整的当前 State
        param1 (int) : 额外整数参数（如阈值、批量大小等）
        param2 (str) : 额外字符串参数（如模型名称、配置项等）
    Returns:
        dict: 增量更新字典
    """
    print(state, param1, param2)              # 打印 State 和额外参数（调试用）
    return {"process_data": {"process": "process_value"}}  # dict: 返回处理结果

# partial(fn, **kwargs) -> Callable: 预绑定 param1、param2，得到只需 state 参数的新函数
process_with_params = partial(process_node, param1=100, param2="test")

graph = StateGraph(dict)                        # StateGraph: 创建图实例（此处用 dict 作示例状态）
# add_node(name, fn): fn 签名变为 fn(state) -> dict，符合节点函数要求
graph.add_node("process", process_with_params)  # 将带参数节点注册到图中
```

### 4.3 节点重试策略（RetryPolicy）

```python
# ============================================================
# 节点重试策略：为不稳定的节点（如网络请求、API 调用）配置自动重试
# 避免因偶发异常导致整个图执行失败
# ============================================================
from functools import partial                    # 导入 partial，绑定额外参数
from langgraph.graph import StateGraph           # 导入 StateGraph
from langgraph.types import RetryPolicy          # 导入重试策略类
# retry_on 接受任意异常类型列表；此处使用 Python 内置异常
# 实际生产中常用 requests.RequestException / httpx.HTTPError 等第三方网络异常


def process_node(state: dict, param1: int, param2: str) -> dict:
    """需要重试的节点函数（模拟会偶发网络错误的 API 调用）"""
    return {"process_data": {"param1": param1, "param2": param2}}   # dict: 返回处理结果

# partial 绑定额外参数，得到符合节点签名 fn(state)->dict 的可调用对象
process_with_params = partial(process_node, param1=100, param2="test")

retry_policy = RetryPolicy(
    max_attempts=3,                               # int: 最多重试次数（含首次执行），超过则抛出异常
    initial_interval=1,                           # float: 首次重试前等待秒数
    backoff_factor=2,                             # float: 退避倍数，每次等待时间 = 上次 × backoff_factor
    jitter=True,                                  # bool: 是否添加随机抖动，True 可避免"重试风暴"
    retry_on=[ConnectionError, TimeoutError]      # List[Exception]: 只对列表中的异常类型触发重试
)
# 重试时间线示例: 1s → 2s → 4s（指数退避 + 随机抖动）

graph = StateGraph(dict)   # StateGraph: 创建图实例（此处用 dict 作示例状态）
# add_node(name, fn, retry_policy=policy): 为该节点绑定重试策略
graph.add_node("process", process_with_params, retry_policy=retry_policy)
```

> **重试触发时机**：节点函数抛出异常时，LangGraph 检查该异常类型是否在 `retry_on` 列表中：
>
> - **在列表中** → 触发重试，按退避策略等待后再次执行该节点
> - **不在列表中** → 直接向上抛出，图执行立即失败
>
>
> | 抛出的异常             | 是否重试       |
> | ----------------- | ---------- |
> | `ConnectionError` | 重试（最多 3 次） |
> | `TimeoutError`    | 重试（最多 3 次） |
> | `ValueError`      | 不重试，直接报错   |
> | `KeyError`        | 不重试，直接报错   |
>
>
> **重试流程（以上述配置为例）**：
>
> ```
> 第 1 次执行 → 抛出 ConnectionError
>     等待 1s（initial_interval=1 + jitter 随机抖动）
> 第 2 次执行 → 再次抛出 ConnectionError
>     等待 2s（1s × backoff_factor=2 + jitter）
> 第 3 次执行 → 仍然失败 → 已达 max_attempts=3 → 抛出异常，图停止
> ```
>
> 若第 1、2 次重试后成功，则正常继续执行后续节点，不影响图的其余流程。

## 五、Edge（边）

```
┌────────────────────────────────────────────────┐
│              LangGraph 边类型                    │
├──────────────┬─────────────────────────────────┤
│ 普通边       │ 固定连接：A → B（无条件跳转）      │
│ 条件边       │ 动态路由：A → (B 或 C 或 D)       │
│ 条件入口点   │ START → (B 或 C 或 D)（入口路由） │
└──────────────┴─────────────────────────────────┘
```

### 5.1 普通边（Normal Edge）

```python
# ============================================================
# 普通边：固定、无条件，执行完源节点后必定跳转到目标节点
# 适用场景：线性流程，节点间执行顺序完全固定
# ============================================================
from typing import TypedDict                         # 导入 TypedDict，定义 State 结构
from langgraph.graph import StateGraph, START, END   # 导入图构建组件

class PipelineState(TypedDict):
    data: str   # str: 在各节点间传递的数据字段

builder = StateGraph(PipelineState)   # StateGraph: 创建图实例

# 假设节点函数已定义（node_a / node_b / node_c 各自执行业务逻辑）
builder.add_node("node_a", lambda s: s)   # 注册节点 node_a（此处用恒等函数示意）
builder.add_node("node_b", lambda s: s)   # 注册节点 node_b
builder.add_node("node_c", lambda s: s)   # 注册节点 node_c

# add_edge(source, target) -> None
# source: str | 特殊节点 START — 边的起点节点名称（或 START）
# target: str | 特殊节点 END   — 边的终点节点名称（或 END）
builder.add_edge(START,    "node_a")   # 图开始时进入 node_a
builder.add_edge("node_a", "node_b")   # node_a 执行后必定进入 node_b
builder.add_edge("node_b", "node_c")   # node_b 执行后必定进入 node_c
builder.add_edge("node_c", END)        # node_c 执行后图结束

# 执行顺序（确定性）:
# START → node_a → node_b → node_c → END
```

### 5.2 条件边（Conditional Edge）

```python
# ============================================================
# 条件边：根据当前 State 动态决定下一个节点
# 适用场景：需要根据业务逻辑分支跳转（如奇偶判断、结果路由等）
# ============================================================
from pydantic import BaseModel                       # 导入 Pydantic，用于定义示例 State
from langgraph.graph import StateGraph, START, END   # 导入图构建组件

class MyState(BaseModel):
    x: int   # int: 用于条件判断的整数字段


def check_x_node(state: MyState) -> dict:
    """check_x 节点：读取 x 值，不修改（路由判断在条件边中进行）"""
    return {}   # dict: 空增量，不修改任何字段

def handle_even_node(state: MyState) -> dict:
    """偶数处理节点"""
    return {}   # dict: 空增量示意

def handle_odd_node(state: MyState) -> dict:
    """奇数处理节点"""
    return {}   # dict: 空增量示意


def is_even(state: MyState) -> bool:
    """
    路由函数：根据 State 返回路由键
    Args:
        state (MyState): 当前 State
    Returns:
        bool: True → 路由到 handle_even；False → 路由到 handle_odd
    """
    return state.x % 2 == 0   # bool: x 为偶数返回 True，奇数返回 False


builder = StateGraph(MyState)                        # StateGraph: 创建图实例
builder.add_node("check_x",     check_x_node)        # 注册 check_x 节点
builder.add_node("handle_even", handle_even_node)    # 注册偶数处理节点
builder.add_node("handle_odd",  handle_odd_node)     # 注册奇数处理节点
builder.add_edge(START, "check_x")                   # START → check_x

# add_conditional_edges(source, path_fn, path_map)
# source   : str  — 源节点名称，执行完该节点后调用路由函数
# path_fn  : Callable[[State], key] — 路由函数，接收 State，返回路由键
# path_map : dict  — 路由键到目标节点名称的映射字典
builder.add_conditional_edges(
    "check_x",          # str: 源节点（执行完 check_x 后路由）
    is_even,            # Callable: 路由函数，返回 True 或 False
    {
        True:  "handle_even",   # 路由键 True → 目标节点 handle_even
        False: "handle_odd",    # 路由键 False → 目标节点 handle_odd
    }
)
builder.add_edge("handle_even", END)   # handle_even 执行后结束
builder.add_edge("handle_odd",  END)   # handle_odd  执行后结束
# 注意：每个没有出边的节点都必须显式连接到 END
#       compile() 时 LangGraph 会校验所有节点均有去向
#       若某节点既无普通出边也无条件出边且未连接 END，编译报错：
#       ValueError: Node `xxx` is a dead-end node.

# 执行流程:
# check_x → is_even(state) 返回 True  → handle_even → END
# check_x → is_even(state) 返回 False → handle_odd  → END
```

### 5.3 条件入口点（Conditional Entry Point）

```python
# ============================================================
# 条件入口点：从 START 开始就进行路由，直接决定进入哪个节点
# 适用场景：根据用户输入内容，在图入口处直接分发到不同处理节点
# ============================================================
from typing import TypedDict                         # 导入 TypedDict
from langgraph.graph import StateGraph, START, END   # 导入图构建组件

class SimpleState(TypedDict):
    user_input: str   # str: 用户输入的文本，用于入口路由判断


def greeting_node(state: SimpleState) -> dict:
    """问候处理节点"""
    return {}   # dict: 空增量示意

def farewell_node(state: SimpleState) -> dict:
    """告别处理节点"""
    return {}   # dict: 空增量示意

def question_node(state: SimpleState) -> dict:
    """问答处理节点"""
    return {}   # dict: 空增量示意


def route_input(state: SimpleState) -> str:
    """
    入口路由函数：根据用户输入内容决定进入哪个处理节点
    Args:
        state (SimpleState): 当前 State，包含 user_input 字段
    Returns:
        str: 路由键字符串，对应 path_map 中的键名
    """
    text = state["user_input"].lower()   # str: 转为小写，统一比较
    if "hello" in text or "hi" in text:
        return "greeting"   # str: 路由到问候节点
    elif "bye" in text:
        return "farewell"   # str: 路由到告别节点
    else:
        return "question"   # str: 路由到问答节点

builder = StateGraph(SimpleState)                    # StateGraph: 创建图实例
builder.add_node("greeting_node", greeting_node)     # 注册问候节点
builder.add_node("farewell_node", farewell_node)     # 注册告别节点
builder.add_node("question_node", question_node)     # 注册问答节点

# 条件入口点：source 传入 START，而非普通节点名
builder.add_conditional_edges(
    START,          # 特殊节点 START: 表示这是入口路由（图开始时执行）
    route_input,    # Callable: 入口路由函数
    {
        "greeting": "greeting_node",   # 路由键 → 目标节点
        "farewell": "farewell_node",
        "question": "question_node",
    }
)
builder.add_edge("greeting_node", END)   # 问候节点执行后结束
builder.add_edge("farewell_node", END)   # 告别节点执行后结束
builder.add_edge("question_node", END)   # 问答节点执行后结束

# 执行流程:
# START → route_input()
#   → "greeting" → greeting_node → END
#   → "farewell" → farewell_node → END
#   → "question" → question_node → END
```

### 5.4 三种边的对比


| 边类型   | API                               | 适用场景    |
| ----- | --------------------------------- | ------- |
| 普通边   | `add_edge(A, B)`                  | 固定线性流程  |
| 条件边   | `add_conditional_edges(A, f, m)`  | 节点间动态路由 |
| 条件入口点 | `add_conditional_edges(START, …)` | 入口动态路由  |

## 六、Graph（图）的构建流程

### 6.1 标准六步流程

```python
# ============================================================
# LangGraph 图的标准六步构建流程
# ============================================================
from typing import TypedDict                         # 导入 TypedDict，定义 State 结构
from langgraph.graph import StateGraph, START, END   # 导入图构建核心类

# ── 第一步：定义 State ─────────────────────────────────────────────────────
class GraphState(TypedDict):
    """图的共享状态结构"""
    process_data: dict   # dict: 各节点处理结果的中间数据容器


# ── 第二步：定义节点函数 ────────────────────────────────────────────────────
def input_node(state: GraphState) -> dict:
    """输入节点：接收初始数据，执行输入处理逻辑"""
    return {"process_data": {"input": "input_value"}}   # dict: 增量更新字典

def process_node(state: dict) -> dict:
    """处理节点：执行核心业务处理逻辑"""
    return {"process_data": {"process": "process_value"}}

def output_node(state: GraphState) -> dict:
    """输出节点：提取最终结果，准备返回给调用方"""
    return {"process_data": state.get("process_data")}   # dict: 透传处理结果


# ── 第三步：创建 StateGraph 实例 ─────────────────────────────────────────────
# StateGraph(schema) -> StateGraph
# schema: Type — State 类型（TypedDict / Pydantic / dict），用于类型校验
graph = StateGraph(GraphState)   # StateGraph: 创建以 GraphState 为状态模式的图实例


# ── 第四步：添加节点 ─────────────────────────────────────────────────────────
# add_node(name, fn) -> None
# name: str      — 节点的字符串标识符，用于 add_edge 引用
# fn  : Callable — 节点函数，签名为 fn(state) -> dict
graph.add_node("input",   input_node)    # 注册输入节点
graph.add_node("process", process_node)  # 注册处理节点
graph.add_node("output",  output_node)   # 注册输出节点


# ── 第五步：添加边（定义执行顺序）────────────────────────────────────────────
graph.add_edge(START,     "input")    # START   → input（图的第一个节点）
graph.add_edge("input",   "process")  # input   → process（线性执行）
graph.add_edge("process", "output")   # process → output
graph.add_edge("output",  END)        # output  → END（图结束）


# ── 第六步：编译图 ─────────────────────────────────────────────────────────
# compile() -> CompiledGraph
# 返回值: CompiledGraph — 同时也是 LangChain Runnable 接口的实现类
#         作为 Runnable，支持 invoke / stream / batch / ainvoke / astream 等标准方法
#         可直接嵌入 LangChain 链（LCEL）中，与其他 Runnable 组合使用
app = graph.compile()   # CompiledGraph(Runnable): 编译后生成可执行的图对象


# ── 执行图 ─────────────────────────────────────────────────────────────────
# invoke(input, config=None) -> dict
# input : dict — 初始 State 字典
# 返回值: dict — 最终 State 字典（所有字段的最新值）
result = app.invoke({"process_data": {"name": "测试数据"}})   # dict: 最终 State
print(result)   # dict: {'process_data': {'process': 'process_value'}}
```

### 6.3 链式 Builder 写法（简洁）

```python
# ============================================================
# 链式写法：将六步流程合并为一条链式调用（更简洁）
# 注意：节点函数名即为节点标识符（add_node 只传函数，自动取函数名）
# ============================================================
from typing import TypedDict                         # 导入 TypedDict
from langgraph.graph import StateGraph, START, END   # 导入图构建组件

class AtguiguState(TypedDict):
    topic: str    # str: 主题字段
    joke:  str    # str: 笑话字段

def refine_topic(state: AtguiguState) -> dict:
    """节点函数：精炼主题"""
    return {"topic": state["topic"] + " and cats"}  # dict: 增量更新

def generate_joke(state: AtguiguState) -> dict:
    """节点函数：生成笑话"""
    return {"joke": f"This is a joke about {state['topic']}"}  # dict: 增量更新

# 链式写法：StateGraph → add_node → add_edge → compile
# 每个方法返回图自身，支持链式调用
graph = (
    StateGraph(AtguiguState)
    .add_node(refine_topic)                  # 只传函数，节点名自动取函数名 "refine_topic"
    .add_node(generate_joke)                 # 节点名自动取函数名 "generate_joke"
    .add_edge(START, "refine_topic")         # START → refine_topic
    .add_edge("refine_topic", "generate_joke")  # refine_topic → generate_joke
    .add_edge("generate_joke", END)          # generate_joke → END
    .compile()                               # CompiledGraph: 编译图
)
```

## 七、特殊 API（Send / Command / RuntimeContext）

| 特性 | `Send` | `Command` | `RuntimeContext` |
| --- | --- | --- | --- |
| **核心用途** | 并行分发：把同一节点以不同参数并行触发多次 | 将"状态更新"和"路由跳转"合并在节点内部一次返回 | 将不可序列化的外部依赖（LLM client、DB 连接等）与 State 分离，通过 config 注入节点 |
| **使用位置** | 条件边路由函数的返回值 | 节点函数的返回值 | 节点函数内部，通过 `config["configurable"]` 读取 |
| **能更新 State 吗** | 否，只负责分发任务 | 是，`update` 字段携带增量更新字典 | 否，`config` 与 State 完全分离，互不相关 |
| **能控制路由吗** | 是，指定目标节点和该次调用的输入 | 是，`goto` 字段指定下一个节点或 `END` | 否 |
| **典型场景** | 对列表中每个元素并行调用同一节点（Map-Reduce） | Agent 节点自主决策：更新数据的同时决定去哪个节点 | 节点内读取 LLM 模型名、DB 连接字符串、API Key 等调用时才确定的参数 |

### 7.1 Send：Map-Reduce 并行分发

**场景**：需要对一个列表中的每个元素并行执行相同节点（同一逻辑处理多份数据）。

```python
# ============================================================
# Send：Map-Reduce 并行分发
# 关键点：Send 允许动态决定并行任务数量，
#         任务数量在运行时根据 State 确定，而非编译时固定
# ============================================================
from typing import Annotated, List, TypedDict    # 导入类型标注工具
import operator                                  # 导入 operator，提供列表追加 Reducer
from langgraph.types import Send                 # 导入 Send 类，用于分发并行任务
from langgraph.graph import StateGraph, START, END  # 导入图构建组件

class AtguiguState(TypedDict):
    subjects: List[str]                             # List[str]: 需要并行处理的主题列表
    jokes:    Annotated[List[str], operator.add]    # List[str]: 收集各并行任务的结果，operator.add 追加合并


# ── Send 的 state 传递机制 ────────────────────────────────────
# Send(node_name, input_dict) 中的 input_dict 是目标节点收到的完整 state
# 与全局 AtguiguState 是替换关系，而非遮盖/合并关系：
#   - 全局 State 完全不传入目标节点，目标节点里访问 state["subjects"] 会直接 KeyError
#   - 目标节点的 state 就只有 input_dict 里的字段，不多不少
# 因此参数类型写 dict 而非 AtguiguState（结构不匹配，写 AtguiguState 会让类型检查器报警告）
# 节点的返回值依然通过 Reducer 合并回全局 State（此处 operator.add 追加 jokes）
def make_joke(state: dict) -> dict:
    """并行任务节点：为单个主题生成一个笑话"""
    # state 此时只有 {"subject": "猫"} 这一个字段，来自 Send 的第二个参数
    subject = state["subject"]             # str: 从 Send 注入的主题
    joke = f"这是一个关于{subject}的笑话"   # str: 生成笑话文本
    return {"jokes": [joke]}               # dict: 返回值通过 operator.add 追加回全局 State


def generate_subjects(state: AtguiguState) -> dict:
    """主节点：生成需要并行处理的主题列表"""
    return {"subjects": ["猫", "狗", "程序员"]}   # dict: 三个主题，后续并行处理


def map_subjects_to_jokes(state: AtguiguState) -> List[Send]:
    """
    路由函数（Map 阶段）：为每个主题创建一个 Send 并行任务
    Args:
        state (AtguiguState): 当前 State，包含 subjects 列表
    Returns:
        List[Send]: Send 对象列表，每个 Send 对应一个并行任务
                    Send(node_name, input_state) -> Send
                    node_name  : str  — 目标节点名称
                    input_state: dict — 注入到目标节点的初始 State 片段
    """
    subjects = state["subjects"]   # List[str]: 读取主题列表
    # Send("make_joke", {"subject": subject})：
    #   第一个参数: str  — 目标节点名称
    #   第二个参数: dict — 目标节点收到的完整私有 state（与全局 State 无关，替换而非合并）
    return [Send("make_joke", {"subject": subject}) for subject in subjects]

# 使用 add_conditional_edges 配合 Send 实现 Map-Reduce
builder = StateGraph(AtguiguState)
builder.add_node("generate_subjects", generate_subjects)  # 注册主节点
builder.add_node("make_joke", make_joke)                  # 注册并行任务节点
builder.add_edge(START, "generate_subjects")              # START → generate_subjects
builder.add_conditional_edges(
    "generate_subjects",      # 源节点
    map_subjects_to_jokes     # 路由函数，返回 Send 列表而非路由键字符串
)
builder.add_edge("make_joke", END)   # 每个并行任务结束后到达 END

graph = builder.compile()   # CompiledGraph: 编译图

# 执行图：触发 Map-Reduce 并行
result = graph.invoke({"subjects": [], "jokes": []})   # dict: 初始 State

# 执行流程（Map-Reduce）:
# generate_subjects → ["猫","狗","程序员"]
#   ↓
# map_subjects_to_jokes 生成 3 个 Send 对象
#   ↓
# make_joke({"subject":"猫"})      ─┐
# make_joke({"subject":"狗"})      ─┼─ 并行执行
# make_joke({"subject":"程序员"})  ─┘
#   ↓
# jokes 列表自动合并（operator.add Reducer）
print(result["jokes"])   # List[str]: ['这是一个关于猫的笑话', '...', '...']
```

### 7.2 Command：状态更新 + 流程跳转合一

**场景**：节点需要同时更新 State **和** 指定下一个节点（Agent 自主决策路由）。

```python
# ============================================================
# Command：将"状态更新"和"路由决策"合并到节点函数内部
# 优势：
#   1. 状态更新和路由决策合并在一个函数中，逻辑更内聚
#   2. 更适合 Agent 节点（节点自己决定去哪里，而非靠外部条件边）
#   3. 支持 goto=END 直接终止流程
# ============================================================
from typing import Annotated, List, TypedDict   # 导入类型标注工具
from langgraph.types import Command             # 导入 Command 类
from langgraph.graph import StateGraph, START, END  # 导入图构建组件

class AgentState(TypedDict):
    messages:      list   # list: 对话消息列表
    task_completed: bool  # bool: 任务是否完成的标志
    current_agent:  str   # str: 当前活跃的 Agent 名称

# Command 支持用方括号填写类型参数：Command[goto目标类型]，作用是告诉类型检查器 goto 允许填哪些值
# （类似 List[int] 表示"整数列表"，Command[Literal["a","b"]] 表示 goto 只能填 "a" 或 "b"）
# 不填类型参数时 goto 不受限制，运行结果与填了完全相同，区别仅在于 IDE 能否提前发现拼写错误
# 返回类型写 Command（不加泛型参数）：
# 因为 goto 可以是节点名字符串 "math_agent" / "default_handler"，也可以是特殊常量 END
# 若要精确标注则需 Command[Literal["math_agent", "default_handler", "__end__"]]，写 Command 更简洁
def decision_agent(state: AgentState) -> Command:
    """
    决策 Agent 节点：根据 State 同时更新数据并决定路由目标
    Args:
        state (AgentState): 当前 State
    Returns:
        Command: 包含 update（增量更新字典）和 goto（目标节点名或 END）的命令对象
                 Command(update=dict, goto=str|END)
    """
    last_msg_content = state["messages"][-1] if state["messages"] else ""   # str: 最后一条消息

    # 任务完成：直接终止图执行
    if state["task_completed"]:
        return Command(
            update={"messages": [("system", "任务完成")]},  # dict: 增量更新消息列表
            goto=END    # 特殊节点 END: 终止图执行
        )

    # 数学问题：路由到数学 Agent
    if "数学" in str(last_msg_content):
        return Command(
            update={"messages": [("assistant", "路由到数学Agent")],
                    "current_agent": "math_agent"},   # dict: 更新消息和当前 Agent
            goto="math_agent"   # str: 动态路由目标节点名称
        )

    # 默认：继续当前处理
    return Command(
        update={"messages": [("assistant", "继续处理")]},
        goto="default_handler"   # str: 默认处理节点
    )

def math_agent(state: AgentState) -> dict:
    """数学处理节点（占位实现，实际场景接入数学专用 LLM）"""
    return {"messages": state["messages"] + [("assistant", "数学处理完成")]}

def default_handler(state: AgentState) -> dict:
    """默认处理节点（占位实现）"""
    return {"messages": state["messages"] + [("assistant", "默认处理完成")]}

# 构建并编译图
graph = StateGraph(AgentState)
graph.add_node("decision_agent",  decision_agent)    # 决策节点
graph.add_node("math_agent",      math_agent)        # 数学处理节点
graph.add_node("default_handler", default_handler)   # 默认处理节点
graph.add_edge(START, "decision_agent")              # 入口 → 决策节点
graph.add_edge("math_agent",      END)               # 数学节点 → END
graph.add_edge("default_handler", END)               # 默认节点 → END
app = graph.compile()   # CompiledGraph: 编译图

# 执行示例
result = app.invoke({
    "messages":      ["请帮我解一道数学题"],
    "task_completed": False,
    "current_agent":  ""
})
print(result["current_agent"])   # str: "math_agent"（已被 Command.update 写入）
```

### 7.3 RuntimeContext：运行时注入依赖

**场景**：节点需要使用 LLM 客户端、数据库连接等外部依赖（这些依赖不适合放在 State 中，因为 State 需要支持持久化与序列化，而 LLM 客户端、DB 连接等往往不可序列化）。LangGraph 1.x 标准方式是通过 `config["configurable"]` 注入，旧版 `Runtime[T]` 签名仅供参考。

```python
# ============================================================
# RuntimeContext：将"外部依赖"从 State 中分离，通过 config["configurable"] 注入
# ──────────────────────────────────────────────────────────
# State（状态）：在节点间流转的业务数据（可序列化、可持久化）
# Context（上下文）：节点运行需要的外部依赖（不可序列化）
#   - LLM client（如 ChatOpenAI 实例）
#   - DB client / Redis client
#   - API Key / 配置对象
# ============================================================
from typing import TypedDict                     # 导入 TypedDict，定义业务 State
from langgraph.graph import StateGraph, START, END  # 导入图构建组件
from langchain_core.runnables import RunnableConfig  # 导入 RunnableConfig，携带运行时配置（含外部依赖）


# ── 业务 State（可序列化，随检查点持久化）─────────────────────────────────────
class AgentState(TypedDict):
    """业务 State：只存放可序列化的业务数据，不放 LLM/DB 等外部依赖"""
    messages:       list   # list: 对话消息列表
    task_completed: bool   # bool: 任务是否完成
    current_agent:  str    # str: 当前活跃的 Agent 名称


# ── config["configurable"] 约定字段（文档说明，无需定义类，LangGraph 不感知此结构）──
# model_name:    str  —— 使用的模型名称，如 "gpt-4-turbo"
# db_connection: str  —— 数据库连接字符串
# api_key:       str  —— API 密钥（不应放在 State 中，避免被持久化）
# 实际传递时直接在 invoke 的 config["configurable"] 字典中提供对应 key 即可


def process_message(
    state: AgentState,
    config: RunnableConfig   # RunnableConfig: LangGraph 自动注入，包含 configurable 字段
) -> dict:
    """
    带 RuntimeContext 的节点函数
    Args:
        state  (AgentState)    : 当前 State（业务数据）
        config (RunnableConfig): LangGraph 自动注入的运行时配置，
                                 通过 config["configurable"] 访问外部依赖
    Returns:
        dict: 增量更新字典
    """
    # config["configurable"] -> dict: 运行时注入的依赖字典
    configurable  = config.get("configurable", {})           # dict: 从配置中读取 configurable 段
    model_name    = configurable.get("model_name", "gpt-4o-mini")   # str: 从配置读取模型名称
    db_connection = configurable.get("db_connection", "")           # str: 从配置读取数据库连接
    # 使用 model_name 初始化 LLM 客户端（此处省略，实际代码中完整实现）
    return {"messages": [f"使用模型 {model_name} 处理完成"]}   # dict: 增量更新

# 创建图（无需声明 context_schema，通过 config["configurable"] 传递外部依赖）
builder = StateGraph(AgentState)                    # StateGraph: 创建以 AgentState 为状态模式的图
builder.add_node("process", process_message)        # 注册带 config 参数的节点
builder.add_edge(START, "process")                  # START → process（入口边，必须）
builder.add_edge("process", END)                    # process → END（出口边，必须）

graph = builder.compile()  # CompiledGraph: 编译图

# 执行时通过 config["configurable"] 注入外部依赖（不放在 State 中）
config_with_context = {
    "configurable": {
        "model_name":    "gpt-4-turbo",        # str: 模型名称
        "db_connection": "postgresql://...",   # str: 数据库连接字符串
        "api_key":       "sk-...",             # str: API 密钥（不应放在 State 中）
    }
}
# invoke(initial_state, config): 将 configurable 按需注入给声明了 config 参数的节点
# LangGraph 内部用 inspect.signature() 扫描每个节点函数的参数列表：
#   - 节点函数有 config: RunnableConfig 参数 → 调用时自动注入 config
#   - 节点函数没有 config 参数            → 只传 state，不报错，正常执行
# 因此图中各节点无需全部声明 config，只有真正需要外部依赖的节点才需要加
result = graph.invoke(
    {"messages": [], "task_completed": False, "current_agent": ""},
    config_with_context   # dict: 运行时配置（含外部依赖）
)   # dict: 最终 State
```

## 八、高级特性：Streaming 流式输出

> **为什么需要 Streaming**：不加 Streaming 的图每次 `invoke` 都要等全部节点执行完毕才返回结果。
> 加上 `stream` 模式后，用户能够即刻看到大模型或 Agent 的回复内容按 Token 逐字生成，
> 实现"边出边看"的效果，显著提升交互流畅感，尤其适合长文本生成、智能助手、代码补全等场景。

### 8.1 三种 Stream 模式

**updates 模式：只看每步的增量**

```python
# ============================================================
# updates 模式：每个节点执行完毕后，立即输出该节点的增量字典
# 适用场景：调试节点输出，监控每步执行结果
# graph 为第 6.3 节链式写法中编译好的 AtguiguState 图（含 refine_topic / generate_joke 节点）
# ============================================================
# graph.stream(input, stream_mode) -> Generator[dict, None, None]
# input      : dict — 初始 State
# stream_mode: str  — "updates"（增量）/ "values"（完整）/ "messages"（Token 流）
for chunk in graph.stream({"topic": "ice cream", "joke": ""}, stream_mode="updates"):
    # chunk -> dict: 格式为 {节点名: 该节点的增量字典}
    print(chunk)
# 输出示例:
# {'refine_topic': {'topic': 'ice cream and cats'}}
# {'generate_joke': {'joke': 'This is a joke about ice cream and cats'}}
```

**values 模式：每步后的完整状态**

```python
# ============================================================
# values 模式：每个节点执行完毕后，输出完整的当前 State
# 适用场景：监控全局状态变化，排查字段被意外覆盖的问题
# graph 为第 6.3 节链式写法中编译好的 AtguiguState 图
# ============================================================
for chunk in graph.stream({"topic": "ice cream", "joke": ""}, stream_mode="values"):
    # chunk -> dict: 当前完整 State 字典（包含所有字段的最新值）
    print(chunk)
# 输出示例:
# {'topic': 'ice cream', 'joke': ''}                                          ← 初始状态
# {'topic': 'ice cream and cats', 'joke': ''}                                 ← refine_topic 后
# {'topic': 'ice cream and cats', 'joke': 'This is a joke...'}                ← generate_joke 后
```

**messages 模式：LLM Token 逐字流式输出**

```python
# ============================================================
# messages 模式：LLM 每生成一个 Token 就立即推送给调用方
# 适用场景：实时对话输出、流式打字效果（ChatGPT 风格）
# graph 为含有 LLM 调用节点的编译好的图（节点内部调用 ChatOpenAI 等 LLM）
# ============================================================
from typing import Annotated, TypedDict                  # 导入类型标注工具
from langgraph.graph import StateGraph, START, END       # 导入图构建组件
from langgraph.graph.message import add_messages         # 导入消息 Reducer
from langchain_openai import ChatOpenAI                  # 导入 LLM
from langchain_core.messages import HumanMessage         # 导入消息类型

class ChatState(TypedDict):
    messages: Annotated[list, add_messages]   # list: 对话历史消息，add_messages 自动追加

llm = ChatOpenAI(model="gpt-4o-mini")        # ChatOpenAI: 初始化 LLM 实例

def chat_node(state: ChatState) -> dict:
    """LLM 对话节点：调用 LLM 生成回复"""
    response = llm.invoke(state["messages"])  # AIMessage: LLM 响应（完整消息对象）
    return {"messages": [response]}           # dict: 追加 AI 回复到消息列表

graph = (
    StateGraph(ChatState)
    .add_node(chat_node)
    .add_edge(START, "chat_node")
    .add_edge("chat_node", END)
    .compile()
)   # CompiledGraph: 编译好的对话图

inputs = {"messages": [HumanMessage(content="写一首关于春天的诗")]}

# graph.stream(input, stream_mode="messages") -> Generator[tuple, None, None]
# 每次 yield 一个元组: (LangChain 消息对象, 元数据字典)
for chunk, meta_data in graph.stream(inputs, stream_mode="messages"):
    # chunk.content -> str: 单个 Token 的文本内容（可能是 1~几个字符）
    if chunk.content:                                    # 过滤空 Token
        print(chunk.content, end="", flush=True)        # 逐 Token 打印，不换行，立即刷新缓冲区
```

### 8.2 三种模式对比


| 模式         | 返回内容         | 适用场景     |
| ---------- | ------------ | -------- |
| `updates`  | 每步节点的增量字典    | 调试节点输出   |
| `values`   | 每步后的完整 State | 监控全局状态变化 |
| `messages` | LLM Token 流  | 实时对话输出   |

## 九、高级特性：持久化（Checkpointer）

不加持久化的图每次 `invoke` 都是 **"失忆"的**——执行完毕，状态消失。

加上 `Checkpointer` 后：

- 每个节点执行后自动保存 **"检查点"（快照）**
- 可以查询执行历史（`get_state_history`）
- 支持多轮对话（**同一 `thread_id` 保持上下文**）
- 支持时间旅行（从任意历史点恢复，见第十章）

### 9.1 InMemorySaver（内存存储，开发测试用）

```python
# ============================================================
# InMemorySaver：将检查点存储在进程内存中
# 优点：零配置，无外部依赖；缺点：进程重启后数据丢失
# 适用场景：开发调试、单元测试
# ============================================================
from typing import Annotated, TypedDict                   # 导入类型标注工具
from langgraph.graph import StateGraph, START, END        # 导入图构建组件
from langgraph.graph.message import add_messages          # 导入消息 Reducer
from langgraph.checkpoint.memory import InMemorySaver     # 导入内存存储 Checkpointer

class ConvState(TypedDict):
    """多轮对话 State：包含消息历史和执行步骤计数"""
    messages:   Annotated[list, add_messages]  # list: 对话消息历史，add_messages 自动追加
    step_count: int                            # int: 执行步骤计数（调试用）

def step_node(state: ConvState) -> dict:
    """示例节点：每次执行将步骤计数加一"""
    return {"step_count": state.get("step_count", 0) + 1}   # dict: 步骤计数递增

builder = StateGraph(ConvState)            # StateGraph: 创建以 ConvState 为状态模式的图
builder.add_node("step", step_node)        # 注册节点
builder.add_edge(START, "step")            # START → step
builder.add_edge("step", END)              # step  → END

# compile(checkpointer=...) -> CompiledGraph: 为图绑定 Checkpointer
app = builder.compile(checkpointer=InMemorySaver())   # CompiledGraph: 带持久化功能的图

# config 字典：通过 thread_id 标识一个会话（同 thread_id 的调用共享历史）
# configurable.thread_id: str — 会话标识符，可以是用户 ID、设备 ID 等
config = {"configurable": {"thread_id": "user_13811112222"}}   # dict: 配置字典

# ── 首次执行（第 1 轮）────────────────────────────────────────────────────
# invoke(input, config) -> dict
# input : dict — 初始 State（本次调用的输入）
# config: dict — 配置字典，包含 thread_id 用于关联历史
result = app.invoke(
    {"messages": [], "step_count": 0},   # dict: 初始 State
    config                               # dict: 配置，关联 thread_id
)

# ── 查询当前状态 ────────────────────────────────────────────────────────────
# get_state(config) -> StateSnapshot
# 返回值: StateSnapshot — 最新检查点的快照对象
saved_state = app.get_state(config)    # StateSnapshot: 最新状态快照
print(saved_state.values)  # dict: 最新 State 的完整字段值（含 step_count）
print(saved_state.next)    # tuple: 下一个待执行节点名称（已完成则为空元组）

# ── 继续执行（第 2 轮，沿用上一轮历史状态）──────────────────────────────────
# invoke(None, config): 传入 None + 同一 config，从上次结束点继续执行
result2 = app.invoke(None, config)   # dict: 接续上一轮，step_count 继续递增

# ── 查看执行历史（检查点列表）──────────────────────────────────────────────
# get_state_history(config) -> Iterator[StateSnapshot]
# 返回值: Iterator[StateSnapshot] — 检查点迭代器，最新在前（栈结构）
for checkpoint in app.get_state_history(config):
    print(checkpoint.values)   # dict: 该历史时刻的完整 State
    print(checkpoint.config)   # dict: 包含 checkpoint_id 的配置信息
```

### 9.2 SqliteSaver（SQLite 持久化，本地开发用）

```bash
# 安装 SQLite Checkpointer（首次使用前执行一次）
pip install langgraph-checkpoint-sqlite   # SQLite 持久化支持包
```

```python
# ============================================================
# SqliteSaver：将检查点持久化到 SQLite 数据库文件
# 优点：持久化（进程重启数据不丢失）；缺点：不支持高并发
# 适用场景：本地开发、单机部署
# ============================================================
import sqlite3                                        # 导入 Python 标准库 SQLite3
from typing import Annotated, TypedDict               # 导入类型标注工具
from langgraph.graph import StateGraph, START, END    # 导入图构建组件
from langgraph.graph.message import add_messages      # 导入消息 Reducer
from langgraph.checkpoint.sqlite import SqliteSaver   # 导入 SQLite Checkpointer

class ConvState(TypedDict):
    """多轮对话 State（与 9.2 节一致，此处重新声明供独立运行）"""
    messages:   Annotated[list, add_messages]   # list: 对话消息历史，add_messages 自动追加
    step_count: int                             # int: 执行步骤计数

def step_node(state: ConvState) -> dict:
    """示例节点：每次执行将步骤计数加一"""
    return {"step_count": state.get("step_count", 0) + 1}

builder = StateGraph(ConvState)      # StateGraph: 创建图
builder.add_node("step", step_node)  # 注册节点
builder.add_edge(START, "step")      # START → step
builder.add_edge("step", END)        # step  → END

# sqlite3.connect(db_path, check_same_thread) -> Connection
# db_path          : str  — SQLite 数据库文件路径（不存在则自动创建）
# check_same_thread: bool — False 允许多线程使用同一连接（LangGraph 需要）
conn = sqlite3.connect("sqlite_data.db", check_same_thread=False)   # Connection: 数据库连接

# SqliteSaver(conn=connection) -> SqliteSaver
# conn: Connection — SQLite 数据库连接对象
sqliteDB = SqliteSaver(conn=conn)   # SqliteSaver: SQLite 持久化 Checkpointer

# compile(checkpointer=sqliteDB): 为图绑定 SQLite Checkpointer
graph = builder.compile(checkpointer=sqliteDB)   # CompiledGraph: 带 SQLite 持久化的图

config = {"configurable": {"thread_id": "user-001"}}         # dict: 配置字典，关联用户会话
result = graph.invoke({"messages": [], "step_count": 0}, config)  # dict: 执行图，状态自动持久化

conn.close()   # 关闭数据库连接（程序结束时调用）
```

### 9.3 Checkpointer 三种方式对比


| Checkpointer    | 存储介质       | 适用场景      |
| --------------- | ---------- | --------- |
| `InMemorySaver` | 进程内存       | 开发测试、单元测试 |
| `SqliteSaver`   | SQLite 文件  | 本地开发、单机部署 |
| `PostgresSaver` | PostgreSQL | 生产环境、高并发  |

## 十、高级特性：时间旅行（Time Travel）

时间旅行允许从任意历史检查点恢复执行：

1. **重放**：从某个历史点原样重新执行（调试用）
2. **修改后重放**：先修改历史状态，再从该点继续执行（产生"平行时间线"）

### 10.1 时间旅行完整使用步骤

```python
# ============================================================
# 时间旅行：查看历史检查点，修改状态后从任意点重新执行
# 前提：图必须配置了 Checkpointer（否则没有历史可回溯）
# ============================================================
import uuid                                               # 导入 uuid，生成唯一会话 ID
from typing import TypedDict                              # 导入 TypedDict
from langgraph.graph import StateGraph, START, END        # 导入图构建组件
from langgraph.checkpoint.memory import InMemorySaver     # 导入内存 Checkpointer

class StoryState(TypedDict):
    """故事生成 State：每个节点负责生成故事的一个部分"""
    character: str   # str: 故事主角（可在时间旅行时修改）
    setting:   str   # str: 故事场景
    plot:      str   # str: 故事情节

def create_character(state: StoryState) -> dict:
    """节点1：创建故事主角"""
    return {"character": state.get("character") or "一位勇敢的骑士"}

def set_setting(state: StoryState) -> dict:
    """节点2：设定故事场景"""
    return {"setting": "神秘的魔法森林"}

def write_plot(state: StoryState) -> dict:
    """节点3：编写故事情节"""
    return {"plot": f"{state['character']} 在{state['setting']}中展开了冒险"}

builder = StateGraph(StoryState)
builder.add_node("create_character", create_character)
builder.add_node("set_setting",      set_setting)
builder.add_node("write_plot",       write_plot)
builder.add_edge(START,              "create_character")
builder.add_edge("create_character", "set_setting")
builder.add_edge("set_setting",      "write_plot")
builder.add_edge("write_plot",       END)

graph = builder.compile(checkpointer=InMemorySaver())   # CompiledGraph: 必须启用 Checkpointer

# ── 第一步：正常执行并保存历史 ─────────────────────────────────────────────
config1 = {"configurable": {"thread_id": str(uuid.uuid4())}}   # dict: 唯一会话 ID
story1 = graph.invoke({"character": "", "setting": "", "plot": ""}, config1)  # dict: 正常执行

# ── 第二步：查看历史检查点（倒序，最新在前）────────────────────────────────
# get_state_history(config) -> Iterator[StateSnapshot]
# StateSnapshot 属性:
#   .next   : tuple — 下一个待执行节点名称（已完成则为空元组）
#   .config : dict  — 包含 checkpoint_id 的配置信息，可直接传给 invoke / update_state
#   .values : dict  — 该时刻的完整 State 字段值
states = list(graph.get_state_history(config1))   # List[StateSnapshot]: 所有历史快照列表
for i, state in enumerate(states):
    print(f"{i}. 下一步节点: {state.next}")                                  # tuple: 待执行节点
    print(f"   检查点ID: {state.config['configurable']['checkpoint_id']}")   # str: 检查点唯一标识
    print(f"   状态值: {state.values}")                                       # dict: 该时刻完整 State

# ── 第三步（可选）：在某个检查点修改状态 ─────────────────────────────────────
# get_state_history 最新在前（倒序），本图有 3 个节点，共 4 个检查点：
#   states[0]: write_plot 执行后（next=()，已结束）
#   states[1]: set_setting 执行后（next=('write_plot',)）
#   states[2]: create_character 执行后（next=('set_setting',)）← 在此修改角色
#   states[3]: 初始状态（next=('create_character',)）
character_state = states[2]   # StateSnapshot: create_character 执行后的检查点

# update_state(config, values) -> dict
# config: dict — 目标检查点的 config（包含 checkpoint_id）
# values: dict — 要修改的字段和新值
new_config = graph.update_state(
    character_state.config,                    # dict: 以该检查点为基准
    values={"character": "一只会飞的龙"}         # dict: 修改 character 字段
)   # dict: 返回新检查点的 config（包含新 checkpoint_id）

# ── 第四步：从新检查点继续执行（产生"平行时间线"）────────────────────────────
# invoke(None, new_config): 传入 None + 新 config，从新检查点继续执行
story2 = graph.invoke(None, new_config)   # dict: 使用修改后的状态继续执行
# story2 使用了新角色"一只会飞的龙"，其余节点从 set_setting 开始继续执行
```

### 10.2 时间旅行的应用场景


| 场景          | 说明                       |
| ----------- | ------------------------ |
| 调试 AI Agent | 分析 LLM 在某一步做了什么决策        |
| 错误恢复        | 某步出错，修复后从该步重新执行          |
| A/B 测试      | 相同起点，不同参数，对比不同执行路径       |

## 十一、高级特性：子图（SubGraph）

子图就是将一个 **编译好的图** 作为另一个图的节点来使用。

```
主图:
START → [子图节点] → END
              ↓
         (子图内部)
    START → [sub_node] → END
```

### 11.1 子图构建与使用

```python
# ============================================================
# 子图：将编译好的子图作为主图的一个节点
# 适用场景：复用逻辑、封装复杂子流程、多 Agent 组装
# ============================================================
from typing import Annotated, List, TypedDict   # 导入类型标注工具
import operator                                 # 导入 operator，提供列表追加 Reducer
from langgraph.graph import StateGraph, START, END  # 导入图构建组件

class AtguiguState(TypedDict):
    messages: Annotated[List[str], operator.add]  # List[str]: 消息列表，追加合并

def sub_node(state: AtguiguState) -> dict:
    """子图内的处理节点：返回对子图消息的响应"""
    return {"messages": ["response from subgraph"]}   # dict: 增量更新消息


# ── 第一步：构建并编译子图 ──────────────────────────────────────────────────
subgraph_builder = StateGraph(AtguiguState)          # 创建子图（使用相同的 State 模式）
subgraph_builder.add_node("sub_node", sub_node)      # 注册子图节点
subgraph_builder.add_edge(START, "sub_node")         # START → sub_node
subgraph_builder.add_edge("sub_node", END)           # sub_node → END
subgraph = subgraph_builder.compile()                # CompiledGraph: 编译子图，得到可复用对象


# ── 第二步：将子图作为节点加入主图 ─────────────────────────────────────────
builder = StateGraph(AtguiguState)
builder.add_node("subgraph_node", subgraph)          # 子图当节点用，name 为 "subgraph_node"
builder.add_edge(START, "subgraph_node")             # START → subgraph_node
builder.add_edge("subgraph_node", END)               # subgraph_node → END
graph = builder.compile()                            # CompiledGraph: 编译主图

# 执行主图
result = graph.invoke({"messages": ["main-graph"]})   # dict: 初始 State
print(result)   # dict: {'messages': ['main-graph', 'main-graph', 'response from subgraph']}
```

### 11.2 状态合并机制（双重合并）

当主图 Reducer 为 `operator.add`（列表拼接）时，状态合并经过 **两次**：

```
初始调用: {"messages": ["main-graph"]}

第一次合并（子图内部）:
  子图接收 ["main-graph"]
  sub_node 返回 ["response from subgraph"]
  子图内部 add → ["main-graph", "response from subgraph"]

第二次合并（主图层面）:
  主图原有 ["main-graph"]
  子图返回 ["main-graph", "response from subgraph"]
  主图 add → ["main-graph", "main-graph", "response from subgraph"]

最终结果: {'messages': ['main-graph', 'main-graph', 'response from subgraph']}
```

> **注意**：这是 `operator.add` Reducer 下子图的正常行为（双重追加），设计时需考虑此特性。

| 价值      | 说明                           |
| ------- | ---------------------------- |
| 复用      | 同一个子图可以被多个主图使用               |
| 封装      | 子图内部逻辑对主图透明，降低耦合             |
| 团队协作    | 不同团队开发不同的子图 / Agent，最后组装     |
| 多 Agent | 每个 Agent 是一个子图，组合成多 Agent 系统 |

## 十二、多 Agent 系统

### 12.1 create_react_agent：快速创建单 Agent

`create_react_agent` 快速创建一个具备 **"思考 → 使用工具 → 再思考"** 循环能力的 ReAct Agent：

```python
# ============================================================
# create_react_agent：一行代码创建具备工具调用能力的 ReAct Agent
# 底层本质：返回一个编译好的 StateGraph（CompiledGraph）
# ============================================================
from langchain_openai import ChatOpenAI            # 导入 OpenAI LLM 适配器
from langgraph.prebuilt import create_react_agent  # 导入 LangGraph 内置 ReAct Agent 创建函数
from langchain_core.messages import HumanMessage   # 导入用户消息类型


def get_weather(city: str) -> str:
    """
    工具函数：获取指定城市的天气信息
    注意：必须有 docstring，LangGraph 将其作为工具描述传给 LLM
    Args:
        city (str): 城市名称
    Returns:
        str: 该城市的天气描述
    """
    return f"今天{city}是晴天，气温 28°C"   # str: 天气描述（实际应接入真实 API）


llm = ChatOpenAI(model="gpt-4o-mini")   # ChatOpenAI: 初始化 LLM 实例

# create_react_agent(model, tools) -> CompiledGraph
# model: BaseChatModel  — LLM 实例（需支持工具调用）
# tools: List[Callable] — 工具函数列表（函数名 + docstring 作为工具描述）
agent = create_react_agent(
    model=llm,              # BaseChatModel: LLM 实例
    tools=[get_weather]     # List[Callable]: 工具函数列表
)   # CompiledGraph: 底层是一个编译好的 StateGraph（ReAct 循环图）

# invoke({"messages": [HumanMessage]}) -> dict
# 返回值: dict — 包含 messages 字段的 State 字典
response = agent.invoke({
    "messages": [HumanMessage(content="今天深圳天气怎么样？")]
})
print(response["messages"][-1].content)   # str: Agent 最终回复内容
```

### 12.2 Supervisor 模式（多 Agent 协调）

```python
# ============================================================
# Supervisor 模式：一个主控 Agent 统一调度多个子 Agent
# 适用场景：多领域任务分发（智能客服、企业助手等）
# ============================================================
from langchain_openai import ChatOpenAI                # 导入 OpenAI LLM
from langgraph.prebuilt import create_react_agent      # 导入 LangGraph 内置 ReAct Agent
from langgraph_supervisor import create_supervisor     # 导入 Supervisor 创建函数


def book_flight(destination: str, date: str) -> str:
    """预订航班工具：预订指定目的地和日期的机票"""
    return f"已成功预订 {date} 飞往 {destination} 的航班"

def book_hotel(city: str, nights: int) -> str:
    """预订酒店工具：在指定城市预订指定天数的酒店"""
    return f"已成功在 {city} 预订 {nights} 晚酒店"


llm = ChatOpenAI(model="gpt-4o-mini")   # ChatOpenAI: 共享 LLM 实例

# 创建子 Agent（每个子 Agent 只负责自己领域的工具）
flight_assistant = create_react_agent(
    model=llm,
    tools=[book_flight],          # 航班工具
    name="flight_assistant"       # str: Agent 名称（Supervisor 路由时使用）
)

hotel_assistant = create_react_agent(
    model=llm,
    tools=[book_hotel],           # 酒店工具
    name="hotel_assistant"        # str: Agent 名称
)

# create_supervisor(agents, model, prompt) -> CompiledGraph
# agents: List[CompiledGraph] — 子 Agent 列表
# model : BaseChatModel       — Supervisor 使用的 LLM
# prompt: str                 — Supervisor 的系统提示词
supervisor = create_supervisor(
    agents=[flight_assistant, hotel_assistant],   # List[CompiledGraph]: 子 Agent 列表
    model=llm,                                    # BaseChatModel: Supervisor LLM
    prompt="你是旅行预订系统的调度主管，根据用户需求路由到对应的预订助手"
).compile()   # CompiledGraph: 编译 Supervisor 图

# 执行 Supervisor
result = supervisor.invoke({
    "messages": [{"role": "user", "content": "帮我预订明天上海飞北京的机票和北京3晚的酒店"}]
})
print(result["messages"][-1].content)   # str: Supervisor 汇总后的最终回复
```

### 12.3 多 Agent 架构模式对比

**Network（网络型）—— 多 Agent 平等协作**

```
Agent A ←→ Agent B
   ↑    ↘ ↙    ↑
   └── Agent C ┘

适合：头脑风暴、并行搜索、信息汇总、研究讨论
典型：研究报告生成（政策/技术/竞品多 Agent 并行分析后汇总）
```

**Supervisor（监督者型）—— 主控 Agent 统一调度**

```
用户请求
   ↓
Supervisor（主管 Agent）
   ├──→ 财务 Agent
   ├──→ IT Agent
   └──→ HR Agent
   ↓
汇总结果 → 用户

适合：企业助手、智能客服、多领域任务路由
```

**Supervisor as Tools（监督者作为工具）**

```
Supervisor
   ├── tool: finance_agent
   ├── tool: it_agent
   └── tool: hr_agent

适合：统一入口、统一上下文控制
优点：主 Agent 持有多个专业工具，决策更集中
```

**Hierarchical（层级型）—— 多层 Supervisor 分级拆解**

```
顶层 Supervisor
   ├── 市场 Supervisor
   │     ├── 政策 Agent
   │     ├── 竞品 Agent
   │     └── 数据 Agent
   └── 技术 Supervisor
         ├── 硬件 Agent
         └── 软件 Agent

适合：大型任务拆解、复杂项目管理、公司或部门结构模拟
```

**Custom（自定义混合型）**

```
用户输入
   ↓
Supervisor 判断
   ├──→ 财务 Agent
   ├──→ IT Agent ←→ 安全 Agent（协作）
   └──→ HR Agent
   ↓
人工审批（HITL - Human In The Loop）
   ↓
最终结果

适合：高度定制的企业级 AI 应用、多步骤业务审批、多部门协作
```

### 12.4 多 Agent 架构模式总结


| 连接方式                | 核心特点             | 适合场景               |
| ------------------- | ---------------- | ------------------ |
| Network             | 多 Agent 平等协作     | 头脑风暴、研究分析、信息汇总     |
| Supervisor          | 主控 Agent 统一调度    | 智能客服、企业助手、任务路由     |
| Supervisor as Tools | 子 Agent 工具化      | 统一入口、统一上下文控制       |
| Hierarchical        | 多层 Supervisor 拆解 | 大型项目、多部门协作、复杂任务规划  |
| Custom              | 按业务自由组合          | 企业级定制流程、人工审批、多系统集成 |


### 12.5 Agent 的四种 Stream 模式

```python
# ============================================================
# create_react_agent 返回的 CompiledGraph 支持四种 stream_mode
# agent 沿用 12.1 节定义：create_react_agent(model=llm, tools=[get_weather])
# ============================================================
from langchain_openai import ChatOpenAI           # 导入 OpenAI LLM 适配器
from langgraph.prebuilt import create_react_agent  # 导入 ReAct Agent 创建函数

def get_weather(city: str) -> str:
    """获取指定城市的天气（工具函数，docstring 作为工具描述传给 LLM）"""
    return f"今天{city}是晴天，气温 28°C"   # str: 天气描述

llm   = ChatOpenAI(model="gpt-4o-mini")           # ChatOpenAI: LLM 实例
agent = create_react_agent(model=llm, tools=[get_weather])  # CompiledGraph: ReAct Agent

for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "今天深圳天气怎么样？"}]},
    stream_mode="values",   # "messages" / "updates" / "values" / "custom"
):
    chunk["messages"][-1].pretty_print()   # 打印最新一条消息（格式化输出）
```


| `stream_mode` | 输出内容             |
| ------------- | ---------------- |
| `messages`    | LLM 逐 token 流式输出 |
| `updates`     | 每步工具调用的增量输出      |
| `values`      | 每步后的完整状态（默认）     |
| `custom`      | 工具内部自定义输出        |

### 13.3 State 定义（graph/state.py）

# ============================================================
# 旅行预订助手的共享状态定义
# ============================================================
from typing import Annotated, List, TypedDict   # 导入类型标注工具
from langgraph.graph.message import add_messages   # 导入消息专用 Reducer


class TravelState(TypedDict):
    """
    旅行预订助手的全局共享 State
    所有节点共享此结构，字段通过对应 Reducer 合并
    """
    # Annotated[List, add_messages]: 消息列表，自动追加+去重，不覆盖
    messages:     Annotated[List, add_messages]  # List: 对话历史消息列表（含 HumanMessage / AIMessage）
    intent:       str   # str: 用户意图识别结果，"flight" / "hotel" / "unknown"
    booking_result: str   # str: 预订操作的结果描述（成功或失败信息）
    step_count:   int   # int: 当前执行步骤计数（用于调试追踪）

### 13.4 节点函数（graph/nodes.py）

```python
# ============================================================
# 旅行预订助手的所有节点函数定义
# ============================================================
import os                                         # 导入标准库，读取环境变量
from dotenv import load_dotenv                    # 导入 load_dotenv，加载 .env 文件
from langchain_openai import ChatOpenAI           # 导入 OpenAI LLM 适配器
from langchain_core.messages import HumanMessage, AIMessage  # 导入消息类型
from graph.state import TravelState               # 导入 State 类型

load_dotenv()   # 加载 .env 文件中的 API Key

# 初始化 LLM 实例（全局共享，避免重复创建）
llm = ChatOpenAI(
    model="gpt-4o-mini",             # str: 使用的模型名称
    temperature=0,                   # float: 0 表示确定性输出（不随机），适合意图识别
    api_key=os.environ.get("OPENAI_API_KEY"),  # str: 从环境变量读取 API Key
)


def intent_recognition_node(state: TravelState) -> dict:
    """
    意图识别节点：分析用户最新消息，判断预订意图
    Args:
        state (TravelState): 当前 State，包含 messages 对话历史
    Returns:
        dict: 增量更新字典，包含 intent 字段和 step_count 递增
    """
    # state["messages"][-1] -> BaseMessage: 获取最新一条用户消息
    last_message = state["messages"][-1]   # BaseMessage: 最新用户消息对象
    user_input = last_message.content      # str: 用户输入的文本内容

    # 调用 LLM 进行意图分类（简单 prompt 方式）
    prompt = f"""分析以下用户输入，判断预订意图，只返回一个词：
    - 如果是预订航班/机票，返回：flight
    - 如果是预订酒店/住宿，返回：hotel
    - 否则返回：unknown
    
    用户输入：{user_input}"""

    # llm.invoke(messages) -> AIMessage
    # 返回值: AIMessage — LLM 返回的消息对象，.content 为文本内容
    response = llm.invoke([HumanMessage(content=prompt)])   # AIMessage: LLM 响应
    intent = response.content.strip().lower()               # str: 提取并标准化意图文本

    # 确保 intent 是有效值
    if intent not in ["flight", "hotel"]:
        intent = "unknown"   # str: 无法识别时标记为 unknown

    return {
        "intent":     intent,                   # str: 识别到的意图
        "step_count": state.get("step_count", 0) + 1  # int: 步骤计数递增
    }


def flight_booking_node(state: TravelState) -> dict:
    """
    航班预订节点：根据用户消息执行航班预订逻辑
    Args:
        state (TravelState): 当前 State
    Returns:
        dict: 增量更新字典，包含预订结果消息和 booking_result
    """
    last_message = state["messages"][-1].content   # str: 用户输入文本

    # 调用 LLM 生成航班预订确认（实际生产中应接入真实预订 API）
    prompt = f"用户想要预订航班：{last_message}。请生成一个友好的预订确认回复，包含航班信息摘要。"
    response = llm.invoke([HumanMessage(content=prompt)])   # AIMessage: LLM 回复
    booking_msg = response.content   # str: 预订确认文本

    return {
        "messages":      [AIMessage(content=booking_msg)],   # AIMessage: 预订确认消息（追加到历史）
        "booking_result": f"航班预订完成：{booking_msg[:50]}...",   # str: 简短预订结果摘要
        "step_count":     state.get("step_count", 0) + 1     # int: 步骤计数递增
    }


def hotel_booking_node(state: TravelState) -> dict:
    """
    酒店预订节点：根据用户消息执行酒店预订逻辑
    Args:
        state (TravelState): 当前 State
    Returns:
        dict: 增量更新字典，包含预订结果消息和 booking_result
    """
    last_message = state["messages"][-1].content   # str: 用户输入文本

    prompt = f"用户想要预订酒店：{last_message}。请生成一个友好的预订确认回复，包含酒店信息摘要。"
    response = llm.invoke([HumanMessage(content=prompt)])   # AIMessage: LLM 回复
    booking_msg = response.content   # str: 预订确认文本

    return {
        "messages":      [AIMessage(content=booking_msg)],   # AIMessage: 预订确认消息（追加到历史）
        "booking_result": f"酒店预订完成：{booking_msg[:50]}...",   # str: 简短预订结果摘要
        "step_count":     state.get("step_count", 0) + 1     # int: 步骤计数递增
    }


def fallback_node(state: TravelState) -> dict:
    """
    兜底节点：意图无法识别时给出友好提示
    Args:
        state (TravelState): 当前 State
    Returns:
        dict: 增量更新字典，包含提示消息
    """
    fallback_msg = "抱歉，我只能帮您预订航班或酒店。请告诉我您需要预订哪种服务？"   # str: 提示文本
    return {
        "messages":      [AIMessage(content=fallback_msg)],   # AIMessage: 兜底提示消息
        "booking_result": "意图识别失败，等待用户重新输入",        # str: 结果描述
        "step_count":     state.get("step_count", 0) + 1       # int: 步骤计数递增
    }
```

### 13.5 图构建（graph/builder.py）

```python
# ============================================================
# 旅行预订助手的图构建逻辑
# ============================================================
import sqlite3                                              # 导入 SQLite3
from langgraph.graph import StateGraph, START, END          # 导入图构建组件
from langgraph.checkpoint.sqlite import SqliteSaver         # 导入 SQLite Checkpointer
from graph.state import TravelState                         # 导入 State 类型
from graph.nodes import (                                   # 导入所有节点函数
    intent_recognition_node,
    flight_booking_node,
    hotel_booking_node,
    fallback_node,
)


def route_by_intent(state: TravelState) -> str:
    """
    路由函数：根据意图识别结果决定跳转到哪个预订节点
    Args:
        state (TravelState): 当前 State，包含 intent 字段
    Returns:
        str: 路由键，对应 path_map 中的键名
    """
    intent = state.get("intent", "unknown")   # str: 读取意图字段，默认 "unknown"
    if intent == "flight":
        return "flight"    # str: 路由到航班预订节点
    elif intent == "hotel":
        return "hotel"     # str: 路由到酒店预订节点
    else:
        return "unknown"   # str: 路由到兜底节点


def build_travel_graph() -> "CompiledGraph":
    """
    构建并编译旅行预订助手图
    Returns:
        CompiledGraph: 带 SQLite 持久化的可执行图对象
    """
    # 创建 SQLite 连接和 Checkpointer
    conn = sqlite3.connect("travel_assistant.db", check_same_thread=False)  # Connection: 数据库连接
    checkpointer = SqliteSaver(conn=conn)  # SqliteSaver: SQLite 持久化 Checkpointer

    # 创建图
    builder = StateGraph(TravelState)  # StateGraph: 以 TravelState 为状态模式

    # 添加节点
    builder.add_node("intent_recognition", intent_recognition_node)  # 意图识别节点
    builder.add_node("flight_booking",     flight_booking_node)      # 航班预订节点
    builder.add_node("hotel_booking",      hotel_booking_node)       # 酒店预订节点
    builder.add_node("fallback",           fallback_node)            # 兜底节点

    # 添加边
    builder.add_edge(START, "intent_recognition")  # 入口 → 意图识别

    # 条件边：根据意图路由到对应预订节点
    builder.add_conditional_edges(
        "intent_recognition",   # 源节点：意图识别完成后路由
        route_by_intent,        # 路由函数：读取 intent 字段返回路由键
        {
            "flight":  "flight_booking",   # 路由键 "flight"  → 航班预订节点
            "hotel":   "hotel_booking",    # 路由键 "hotel"   → 酒店预订节点
            "unknown": "fallback",         # 路由键 "unknown" → 兜底节点
        }
    )

    # 所有预订节点和兜底节点执行完毕后到达 END
    builder.add_edge("flight_booking", END)   # 航班预订完成 → END
    builder.add_edge("hotel_booking",  END)   # 酒店预订完成 → END
    builder.add_edge("fallback",       END)   # 兜底处理完成 → END

    # 编译图（绑定 SQLite Checkpointer 实现多轮对话记忆）
    return builder.compile(checkpointer=checkpointer)  # CompiledGraph: 可执行图
```

### 13.6 主程序入口（main.py）

```python
# ============================================================
# 旅行预订助手主程序：命令行交互式多轮对话
# ============================================================
from langchain_core.messages import HumanMessage   # 导入用户消息类型
from graph.builder import build_travel_graph        # 导入图构建函数

def main():
    """主函数：启动旅行预订助手的多轮对话循环"""
    print("=" * 50)
    print("  欢迎使用旅行预订助手！")
    print("  输入 'quit' 退出，输入 'history' 查看历史")
    print("=" * 50)

    # 构建图
    app = build_travel_graph()   # CompiledGraph: 带 SQLite 持久化的可执行图

    # thread_id 对应用户会话（实际生产中应使用用户 ID 或 session ID）
    thread_id = "demo_user_001"   # str: 固定 thread_id，模拟同一用户多轮对话
    config = {"configurable": {"thread_id": thread_id}}  # dict: 图执行配置

    while True:
        user_input = input("\n您: ").strip()   # str: 用户输入（去除首尾空格）

        if user_input.lower() == "quit":
            print("再见！")
            break

        if user_input.lower() == "history":
            # 查看对话历史
            print("\n── 对话历史 ──")
            for i, checkpoint in enumerate(app.get_state_history(config)):
                state_vals = checkpoint.values   # dict: 该历史时刻的 State
                msgs = state_vals.get("messages", [])   # List: 消息列表
                print(f"检查点 {i}: 消息数={len(msgs)}, 意图={state_vals.get('intent', 'N/A')}")
            continue

        if not user_input:
            continue   # 空输入跳过

        # 构造初始 State（只包含本次用户消息）
        initial_state = {
            "messages":      [HumanMessage(content=user_input)],   # List: 用户消息
            "intent":        "",       # str: 意图字段初始为空，由节点填充
            "booking_result": "",      # str: 预订结果初始为空
            "step_count":    0,        # int: 步骤计数初始为 0
        }

        print("\n助手: ", end="", flush=True)

        # 使用 stream 模式逐步输出（values 模式监控每步完整 State）
        final_state = None
        for chunk in app.stream(initial_state, config, stream_mode="values"):
            final_state = chunk   # dict: 每步后的完整 State，保留最后一步
            # 如果有新消息（最新消息是 AIMessage），则打印
            if chunk.get("messages"):
                last_msg = chunk["messages"][-1]   # BaseMessage: 最新消息
                if hasattr(last_msg, "type") and last_msg.type == "ai":
                    print(last_msg.content)   # str: 打印 AI 回复内容

        # 打印预订摘要
        if final_state and final_state.get("booking_result"):
            print(f"\n[预订结果] {final_state['booking_result']}")

if __name__ == "__main__":
    main()   # 启动主程序
```

## 十四、总结

### 14.1 LangGraph 核心知识点回顾


| 知识点            | 关键 API                                                    | 说明                            |
| -------------- | --------------------------------------------------------- | ----------------------------- |
| State 定义       | `TypedDict` / `Pydantic` / `dict`                         | 定义节点间共享的数据容器                  |
| Reducer        | 默认覆盖 / `operator.add` / `add_messages` / 自定义函数            | 控制 State 字段的合并方式              |
| Node 函数        | `fn(state) -> dict`                                       | 执行业务逻辑，返回增量字典                 |
| 带参数 Node       | `functools.partial(fn, **kwargs)`                         | 为节点绑定额外参数                     |
| 重试策略           | `add_node(name, fn, retry_policy=RetryPolicy(...))`       | 为不稳定节点配置自动重试                  |
| 普通边            | `add_edge(A, B)`                                          | 固定线性流程                        |
| 条件边            | `add_conditional_edges(A, fn, map)`                       | 动态路由                          |
| 条件入口点          | `add_conditional_edges(START, fn, map)`                   | 入口动态路由                        |
| 图构建六步          | `StateGraph → add_node → add_edge → compile`              | 标准构建流程                        |
| 可视化            | `print_ascii()` / `draw_mermaid()` / `draw_mermaid_png()` | 调试图结构                         |
| Send           | `Send(node_name, input_state)`                            | Map-Reduce 并行分发               |
| Command        | `Command(update=dict, goto=str)`                          | 状态更新 + 路由合一                   |
| RuntimeContext | `config["configurable"]` + `RunnableConfig`               | 运行时注入外部依赖                     |
| Streaming      | `graph.stream(input, stream_mode=...)`                    | 流式输出（updates/values/messages） |
| 内存持久化          | `InMemorySaver`                                           | 开发测试用                         |
| SQLite 持久化     | `SqliteSaver(conn=conn)`                                  | 本地开发用                         |
| 生产持久化          | `PostgresSaver`                                           | 生产环境高并发                       |
| 时间旅行           | `get_state_history` + `update_state` + `invoke(None)`     | 历史回溯与修改重放                     |
| 子图             | `subgraph.compile()` → `builder.add_node(sub)`            | 复用 / 封装子流程                    |
| 单 Agent        | `create_react_agent(model, tools)`                        | LLM + 工具循环 ReAct Agent        |
| 多 Agent 协调     | `create_supervisor(agents, model, prompt)`                | 主控 Agent 统一调度                 |
